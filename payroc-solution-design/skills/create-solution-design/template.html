Section 8.0 · Always required

Authentication

All API access starts with an OAuth-style token exchange using the API key Payroc issues via a one-time-use link.

EnvironmentEndpoint
ProductionPOST https://identity.payroc.com/authorize
UATPOST https://identity.uat.payroc.com/authorize
  • Send the API key in the x-api-key header.
  • Response returns a Bearer token, valid for 1 hour — refresh server-side, not in the browser.
  • Base API URL differs from the identity URL: https://api.payroc.com/v1/ (prod) / https://api.uat.payroc.com/v1/ (UAT).

8.1 Boarding & Merchant Management

Registers the merchant's legal business, ownership, and pricing with Payroc so a live MID can be issued. Required for every partner.

Boarding is Payroc Boarding API only. The Worldnet Boarding API is not supported in this Solution Design — flag it for follow-up outside the SD.

Decisions to confirm

  • Pricing model: reusable Pricing Intent vs. inline pricing agreement per merchant.
  • Signature capture method: requestedViaEmail vs. requestedViaDirectLink.
  • How many Processing Accounts (MIDs) per Merchant Platform in one submission.
  • Status detection: polling vs. webhook (see §8.9).
  • Owner/control-prong data: at least one control prong + one authorized signatory (can be the same person).

Path to first UAT boarding submission

  1. Exchange API key for Bearer token.
  2. If using a Pricing Intent, create it first — it must exist before the merchant platform references it.
  3. Build the business object + processingAccounts[] array (owners, contacts, funding account, volume mix summing to 100%).
  4. POST /v1/merchant-platforms with a fresh Idempotency-Key.
  5. Persist the returned merchantPlatformId and processingAccountId(s).
  6. Poll or subscribe to the status change from pending to active.

8.2a Hosted Fields — embedded checkout

Payroc's secure card-entry fields embedded directly inside the partner's own checkout page via iframes — the customer never leaves the partner's site, and raw card data never touches partner servers.

Decisions to confirm

  • Payment method: card vs. ACH vs. PAD (one per page).
  • Transaction type: one-time sale, tokenize-for-later, or recurring (tokenization is a prerequisite for recurring).
  • 3-D Secure/SCA required? Payroc support must separately enable the terminal and register a webhook URL — plan for manual turnaround.
  • Styling approach (CSS via the SDK's styles config) and whether custom fields are needed on the same page.

Path to first UAT transaction

  1. Server exchanges API key for Bearer token.
  2. Server creates a short-lived Hosted Fields session, scoped per checkout — expires in 10 minutes, never reused.
  3. Front-end loads Payroc's JS library and initializes hosted fields against the session token.
  4. Customer enters card details; SDK fires a success callback with a single-use token.
  5. Server sends that token to POST /v1/payments with a fresh Idempotency-Key.
  6. Server reads transactionResult.status — HTTP 201 confirms the request was processed, not that it was approved.

Endpoints

MethodEndpointPurposeStatus
POST/processing-terminals/{id}/hosted-fields-sessionsCreate a session token for the embedded formRequired
POST/paymentsSubmit the tokenized paymentRequired
GET/payments/{id}Retrieve a paymentOptional
POST/payments/{id}/capture · /adjust · /reverse · /refundCapture / adjust / void / refundOptional

Common pitfalls: expired/reused session token; SDK init firing before script load (fails silently); branching success only on "approved" and missing the valid "ready" state; CSP blocking the Payroc CDN/iframe origins.

8.2b Hosted Payment Pages — redirect checkout

Worldnet Hosted Pages (HPP) — Worldnet platform

Form POST (or iframe) to a Worldnet-hosted page: the cardholder enters card data on Worldnet's page, Worldnet sends the result — with a response HASH — to the Receipt URL and optionally to a server-to-server Validation URL. 3DS, AVS, DCC and wallets are enabled by terminal configuration.

Decisions to confirm

  • Redirect vs. iframe embed (INIFRAME=Y; a sandboxed iframe needs allow-same-origin).
  • Pre-authorization needed? (terminal must allow pre-auth; completion via Selfcare or REST capture).
  • Save cards (securecardpage → CARDREFERENCE) and/or subscriptions (subscriptionpage/register).
  • Card only, or card + bank transfer on the same page (PAYMENTOPTIONS, SECCODE).
  • Background validation enabled (Validation URL must reply exactly OK).
  • 3DS / DCC / Apple Pay / Google Pay needed (terminal configuration; wallets and DCC are Elavon terminals only).

Endpoints

MethodEndpointPurposeStatus
POST/merchant/paymentpageHosted payment (and card + bank transfer)Required
POST/merchant/preauthpageHosted pre-authorization (same body as payment)If pre-auth
POST/merchant/securecardpageRegister / update a secure token (ACTION)If saving cards
POST/merchant/subscriptionpage/registerRegister a subscription on a stored tokenIf subscriptions
POST/merchant/mpi3D Secure (MPI) for direct integrationsIf 3DS (non-HPP)
POST/merchant/bulkpayments/submitBulk payments (CSV, async; result fetched by BULKID)Optional

Common pitfalls: hash is SHA-512 of the colon-joined fields that are present plus the terminal secret (omit absent fields and their separators; multi-currency terminals add CURRENCY); always verify the response hash and store UNIQUEREF; Receipt URL, Validation URL, "Allow Internet" and similar Selfcare terminal settings are hidden dependencies, several set by Worldnet support. All hosts above are sandbox (testpayments.worldnettps.com).

Not documented in the Worldnet snapshot (confirm with Product): production URLs for each hosted page; retry cadence for validation webhooks and receipt redirects.

Source: worldnet-reference/references/hosted-pages.md, references/auth-and-signatures.md — snapshot date in Appendix A › Provenance. Worldnet Boarding API is not supported in this Solution Design.

A Payroc-hosted payment page the customer is redirected to, then returned from — covers one-time sales, pre-authorizations, saved cards, and gateway-managed recurring billing.

Decisions to confirm

  • Transaction type: sale only, pre-auth (hold/capture), or both (pre-auth unavailable alongside dual pricing/surcharge programs).
  • Recurring/saved cards via Payroc's gateway (Payment Plans + Subscriptions) vs. the partner's own billing software driving MITs against a saved token.
  • Optional server-to-server Background Validation webhook for reconciliation.
  • Receipt URL and (if saving cards) Secure Token URL, both registered in the Self-Care Portal.

Path to first UAT transaction

  1. Configure a terminal secret in the Self-Care Portal (Payroc cannot supply this).
  2. Build and verify the HMAC hash per Payroc's signing recipe (sale hash includes AMOUNT; save-card hash does not).
  3. POST the payment form to Payroc's hosted endpoint.
  4. Customer completes payment; Payroc redirects (GET) to the receipt URL with RESPONSECODE and UNIQUEREF/CARDREFERENCE.
  5. Verify the response hash before trusting any returned field.
  6. For pre-auth: call the Capture API afterward and confirm transactionResult.

8.2e Direct API Payments — server-to-server / MOTO

Worldnet Merchant REST API — card & bank transfer — Worldnet platform

JSON REST API under /api/v1 (sandbox base https://testpayments.worldnettps.com/merchant): API key exchanged for a JWT Bearer token, HATEOAS links, cursor pagination. Covers authorize/sale/pre-auth over POS, eCommerce and MOTO channels, refunds, reversals and ACH/PAD.

Decisions to confirm

  • Retry/duplicate protection strategy — no Idempotency-Key header is documented.

8.2f Worldnet SDKs, POS & plugins — gochip, Websockets, shopping carts

Worldnet only

Worldnet's card-present and plugin integrations. gochip is the card-present stack: a Websockets service (recommended by the Worldnet docs; JSON REQ_*/RES_* messages from any language) or native SDKs (Android, iOS, Windows .NET C#, Java, Ubuntu/Linux) over IDTech, Ingenico, PAX and BBPOS devices. E-commerce plugins and the legacy XML API are alternative paths.

A native-SDK project is more than API calls: it carries device prerequisites, a mandatory logging pipeline, credential provisioning and a device certification pass. The blocks below make that scope explicit so it is agreed before build starts.

Hardware, key injection (RKI / KIF), PIN vs. data keys and terminal-estate management: see 8.6b Card-present operational requirements — these are open questions for every card-present partner.

Decisions to confirm

  • Integration option: Websockets (any language) vs native SDK vs plugin vs legacy XML.
  • SDK platforms in scope (tick all): Android · iOS · Windows (.NET) · Java · Ubuntu/Linux — and the app language/runtime for each (see platform table).
  • Solution line and devices: POS (IDTech, Ingenico, PAX) vs mPOS (BBPOS, Android/iOS). PAX apps run on the device itself and are distributed through PAXstore.
  • Device models and connection types per platform (see device matrix): each combination the partner will deploy must be tested.
  • Flow: basic sale/refund/reversal, pre-auth + tip adjust (uniqueRef), polling mode (unattended; needs Quick Chip), delayed-auth mode, offline mode, Quick Chip vs Standard EMV.
  • Extras: secure tokens (verify token flow support), loyalty (Google Smart Tap / Apple VAS / MIFARE — the partner holds those keys), EBT (PAX; needs the EBT PIN key), Reward Pay surcharging (BBPOS requires manual signature collection), frictionless payment, manual keyed entry.
  • Authentication and provisioning: Terminal ID + API key (+ Integration ID for ISV accounts) per terminal, issued by Payroc; where credentials are held (never hard-coded in a distributed app) and how a device is registered to its Terminal ID.
  • Logging: who hosts the log-upload endpoint and which remote trigger is used (see "Logging & support requirements" below) — this is a partner build item, not optional.
